# Continuous improvement audit — September 12, 2026

This is an ongoing audit, not certification of every file or professional
workflow. The starting revision was `d2e0cf1`; its 1,546 unit tests passed.
The repository inventory includes the React interface, rules and notation,
study/review persistence, library workers, engine wrapper, WASM build patches,
deployment configuration, and browser regression scripts. Detailed inspection
continues in focused passes. No engine-strength improvement is claimed here.

## Retain tournament preparation before the first move

A browser reproduction entered players and an event beside a starting-position
note, then erased the note. The game-details editor disappeared and automatic
recovery cleared the study, discarding the tournament details on reload.
The storage reader also rejected a metadata-only game, and the PGN importer
refused the resulting move-free record.

Normalized game details now count as study content for library storage,
automatic recovery and PGN copy/download/import. The collapsed details editor
is available before the first move. Whitespace, unknown fields and malformed
metadata do not create empty recovery prompts. Removing the last note keeps
the remaining details visible and recoverable. Share URLs still carry positions,
lines and notes; they do not carry tournament metadata, so a metadata-only
draft does not enable Copy Link.

The new browser regression failed against the original code, then passed at
1440, 390 and 320px. It exercises save, recovery, library search/load, PGN copy
and download, reimport, empty reset, and horizontal overflow. The phone
screenshot was inspected. Unit regressions cover storage normalization,
recovery and rejecting invalid move text even when PGN headers are present.
TypeScript, lint, all 1,549 unit tests, engine contract and server-header checks
pass. Browser QA is repeated after committing; the broader baseline matrix
uses the previous fixed production build.

Post-commit QA for `0fe1f2e` passed all nine combinations of Chromium,
WebKit and Firefox with 1440, 390 and 320px viewports against the dev server.

## Reuse the stored study tree while navigating

Ten backwards steps through a 1,024-ply annotated study produced ten new
serialized trees despite leaving every move and annotation unchanged.
`currentGameSnapshot` included the serialization in a memo that also depended
on the cursor and tournament fields. A separate, single-result memo now holds
the serialized tree while those other snapshot fields change. It invalidates
when the source tree changes or a compact straight line needs to retain its
continuation beyond the saved cursor.

The browser regression observes committed React 18 memo values, with a guard
that it found the populated snapshot. It failed with ten tree replacements
before this change; afterwards it observes zero for the same ten steps and
zero while typing "Autumn Cup" into Event. It verifies a subsequent note edit
does invalidate the tree, both old/new notes and all 1,024 moves survive, reload
restores ply 1,014, and unannotated lines still use compact storage at their end
but retain a tree when saved earlier. Chromium passes at 1440/390/320px.
These are avoided allocations and traversals, not measured frame-time or
engine-speed improvements. The React probe requires review on a major upgrade.

Post-commit QA for `946fe08` passed all nine Chromium/WebKit/Firefox and
1440/390/320px combinations against the dev server.

## Repair two stale browser checks

The baseline production matrix exposed two failures in both Chromium and
WebKit, before the new fixes entered that production build. The saved-analysis
test ran the letter shortcut E after the command palette restored focus to a
note textarea. The app correctly treated it as note text, so the Engine panel
never opened. That step now uses the Engine panel command. The score-kind test
saved an intermediate position but expected an unqualified library score. It
now asserts the saved move path and the existing "Saved position:" label for
both numeric and mate readings. These repair test assumptions, not app behavior.

Both new regressions are included in the development audit and production
cross-browser runners.

Post-commit QA for `28df230` passed both repaired workflows at 1440/390/320px
in Chromium, WebKit and Firefox against the dev server.

## Make game details usable with touch and enlarged text

The details disclosure failed the app's 44px touch-target convention. Its
12–16px fixed font sizes also ignored the enlarged root text used elsewhere
in the interface. Text now uses relative sizing; inputs retain a 16px floor.
A container query switches the fields to one column when their panel is
narrow relative to the text size, retaining the compact two-column default
on an ordinary phone. Touch disclosure height is at least 44px.

The browser regression failed on the original disclosure target. It now
checks 100% and 200% text at 1440×900, 390×844, 320×480 and 844×390, opening
and closing the details and tapping/editing all six fields after scrolling.
It checks visible label/input font sizes, target bounds, column reflow and
horizontal overflow. Chromium passes; the short-phone enlarged-text screenshot
was inspected. The workflow is included in both browser audit runners.
This follows W3C guidance for
[reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html) and
[enhanced target size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-enhanced.html),
without claiming full WCAG conformance or a physical-phone keyboard test.

## Engine research and priorities

[Pikafish](https://github.com/official-pikafish/Pikafish) is the relevant
Stockfish-derived Xiangqi engine. Its
[UCI documentation](https://github.com/official-pikafish/Pikafish/wiki/UCI-&-Commands)
describes runtime option discovery, setting Hash after Threads, single-PV
search for best performance, and readiness barriers. Its WDL output models
engine self-play, so those figures should not be presented as a beginner's
personal winning probability. The documentation itself lists different MultiPV
maxima in its example and prose; the engine's advertised options are the
appropriate authority for a particular binary.

The current app already uses SIMD, workers, bounded search scheduling and
separate beginner opponents. Raising the thread count blindly is inappropriate:
the configured eight-thread limit depends on the twelve-worker WASM pool.
The local NNUE file is about 51 MiB, whereas each WASM core is under 700 KiB.
Cold-start transfer and peak memory deserve separate measurements from search
throughput. Browser battery and thermal behavior still need physical devices.

Professional priorities to investigate next: larger study/library capacity,
incremental persistence and indexing, full tournament-header round-trips,
repertoire practice across variations, and reliable saved analysis provenance.
Beginner priorities: clear explanations of threats and evaluation uncertainty,
progressive access to engine controls, and completing play/training workflows
on short screens with enlarged text. Existing features and regressions should
be extended before adding duplicate controls.
