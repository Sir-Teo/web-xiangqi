## Reuse the stored study tree while navigating

Ten backwards steps through a 1,024-ply annotated study produced ten new
serialized trees despite leaving every move and annotation unchanged.
`currentGameSnapshot` included the serialization in a memo that also depended
on the cursor and tournament fields. A separate, single-result memo now holds
the serialized tree while those other snapshot fields change. It invalidates
when the source tree changes or a compact straight line needs to retain its
continuation beyond the saved cursor.

The browser regression observes committed React 18 memo values, with a guard
that it found the populated snapshot. It failed with ten tree replacements
before this change; afterwards it observes zero for the same ten steps and
zero while typing "Autumn Cup" into Event. It verifies a subsequent note edit
does invalidate the tree, both old/new notes and all 1,024 moves survive, reload
restores ply 1,014, and unannotated lines still use compact storage at their end
but retain a tree when saved earlier. Chromium passes at 1440/390/320px.
These are avoided allocations and traversals, not measured frame-time or
engine-speed improvements. The React probe requires review on a major upgrade.

## Engine research and priorities

[Pikafish](https://github.com/official-pikafish/Pikafish) is the relevant
Stockfish-derived Xiangqi engine. Its
[UCI documentation](https://github.com/official-pikafish/Pikafish/wiki/UCI-&-Commands)
describes runtime option discovery, setting Hash after Threads, single-PV
search for best performance, and readiness barriers. Its WDL output models
engine self-play, so those figures should not be presented as a beginner's
personal winning probability. The documentation itself lists different MultiPV
maxima in its example and prose; the engine's advertised options are the
appropriate authority for a particular binary.

The current
[Stockfish protocol reference](https://official-stockfish.github.io/docs/stockfish-wiki/UCI-Protocol-and-Stockfish-Commands.html)
also distinguishes readiness synchronization from search completion. The
queue must continue waiting for bestmove after Stop; readyok alone is not a
finished search. For frontend comparisons,
[Chessground's SVG renderer](https://github.com/lichess-org/chessground/blob/master/src/svg.ts)
skips synchronization when its complete drawing hash is unchanged. This app
already has drawing-prop reuse and regression coverage for that principle;
the new snapshot memo applies reuse to a different expensive representation.

The current app already uses SIMD, workers, bounded search scheduling and
separate beginner opponents. Raising the thread count blindly is inappropriate:
the configured eight-thread limit depends on the twelve-worker WASM pool.
The local NNUE file is about 51 MiB, whereas each WASM core is under 700 KiB.
Cold-start transfer and peak memory deserve separate measurements from search
throughput. Browser battery and thermal behavior still need physical devices.

The new production build's largest JavaScript chunk is 521.34 kB minified,
161.56 kB gzip, and triggers Vite's 500 kB warning. Further extraction of
infrequently used panels from the large App component is a concrete startup
and maintenance candidate. Measure parse/execute costs before treating a
smaller bundle as the largest latency win; the engine-weight transfer is much
larger, and several library/review components are already loaded lazily.

Professional priorities to investigate next: larger study/library capacity,
incremental persistence and indexing, full tournament-header round-trips,
repertoire practice across variations, and reliable saved analysis provenance.
Beginner priorities: clear explanations of threats and evaluation uncertainty,
progressive access to engine controls, and completing play/training workflows
on short screens with enlarged text. Existing features and regressions should
be extended before adding duplicate controls.

## Avoid a duplicate NNUE buffer during engine loading

The wrapper downloaded the 53,719,310-byte network and `FS.writeFile` then
allocated another buffer containing all of it. The shipped Emscripten MEMFS
implementation supports adopting a write buffer with `canOwn`, as documented
in its [filesystem implementation](https://github.com/emscripten-core/emscripten/blob/main/src/lib/libmemfs.js).
The wrapper now transfers ownership of its private download buffer when the
unused capacity is at most 64 KiB. This tolerates small encoded Content-Length
differences without retaining a large streaming-growth buffer. Direct
caller-supplied Uint8Arrays still get copied so later caller mutations cannot
change the loaded file. General filesystem writes retain their existing
copying behavior.

A browser regression instruments the real shipped MEMFS, rather than mocking
the ownership option. It failed before the change and now observes shared
buffer identity for exact lengths and slightly oversized encoded hints. It
also checks complete network contents, compact storage after an unknown-length
stream, caller mutation isolation, and a real depth-one Pikafish search.
This avoids one network-sized allocation/copy at the load step, not the
network transfer itself, all engine memory, or a measured browser RSS reduction.
The source template and distributed wrappers remain identical. The regression
is included in both browser audit runners; engine contract, lint and both
real threaded/single-worker smoke checks pass.

Post-commit QA for `16b5ed0` passed the memory and worker-progress workflows
in Chromium, WebKit and Firefox against the production output. Real production
startup also passed header-based isolation, Pages-style service-worker
isolation and legacy-worker migration.

## Make engine readiness barriers wait for a new reply

Both direct and worker wrapper APIs implemented `uci()` and `isReady()` using
a history-reading `waitForLine`. After the first handshake, an old `uciok` or
`readyok` could satisfy the next request, including a request for which the
engine never replied. This affects wrapper consumers such as the benchmark
harness; the React engine hook manages its own acknowledgment listener.

These command helpers now explicitly request a fresh line. Generic
`waitForLine` retains its existing history-reading default, with `fresh: true`
available for callers waiting on a new command. A deterministic browser
regression uses the real wrapper and worker messaging but holds engine-core
acknowledgments until an explicit release command. It checks repeated UCI and
readiness requests, timeouts when replies are withheld, and compatibility of
history lookup. The old code incorrectly completed the no-reply request;
the updated code waits and times out as specified. This implements the
[Stockfish readiness handshake](https://official-stockfish.github.io/docs/stockfish-wiki/UCI-Protocol-and-Stockfish-Commands.html),
which remains distinct from waiting for `bestmove` to finish a search.
