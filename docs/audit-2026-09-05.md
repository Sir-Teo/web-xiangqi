# Repository audit — September 5, 2026

The strongest next investment is trustworthy study/library workflows and beginner orientation. This already has a capable Xiangqi engine integration; replacing Pikafish or adding more toolbar buttons would miss the larger gaps.

This audit traced the rules/FEN, persistence, explorer, engine queue/worker, review, import/export, board, library, responsive layout, build and CI paths, and exercised the existing regression suites. It is not a claim that every possible interaction or every engine binary instruction has been verified. Generated engine artifacts were checked with contract, smoke, parity and production-browser tests rather than edited.

## Remaining bugs and limits, in priority order

### P1 — Saving game 501 silently removes game 1

`saveGame` in `src/utils/gameLibrary.ts` still writes `games.slice(-MAX_SAVED_GAMES)`. The existing unit test explicitly expects eviction at 500. That behavior is inappropriate for a professional's study collection, even though it is intentional in the current implementation.

Change the storage contract to reject additions at capacity, explain the capacity in the UI, and offer complete backup/export and deliberate removal. Do not silently exchange one user's game for another. Preserve existing data during an IndexedDB migration. Acceptance: a 501st save leaves all 500 originals intact and gives a useful next action.

### P2 — Imported FEN and the board editor enforce different validity rules

`parseRootPositionFromFen` in `src/hooks/useXiangqi.ts` and `normalizeStartFen` in `src/utils/gameLibrary.ts` check generals/check, but omit the piece counts and allowed advisor/elephant/soldier points enforced by `describeSetupProblem` in `src/utils/positionSetup.ts`.

Browser reproduction: load this FEN using `?fen=` or the importer:

```text
rnbakabnr/9/1c5c1/p1p1p1p1p/9/9/PPP1P1P1P/1C5C1/9/RNBAKABNR w - - 0 1
```

It loads 33 pieces with no notice, including six red soldiers and a soldier on b3. Use one shared position-validation policy across editor/import/storage. If impossible composition positions are supported deliberately, mark them explicitly instead of presenting them as ordinary legal positions.

### P2 — Cloud repetition results lack the book's current-position guard

The cloud book consumer checks the returned FEN. The cloud rule consumer in `src/App.tsx` uses `banned`/`drawing` without comparing `cloudRule.key` to the current root and line. Source inspection indicates a stale verdict can be rendered between navigation and the effect that clears it. Add a current-key guard and a delayed-response navigation regression. Unlike the book, rule loading/failure is also not explained in the repetition notice. A missing ruling should not look like a verified absence of forbidden moves.

### P2 — A damaged library is protected but still looks empty

`loadAllGames()` exposes only an array. The write protection added here prevents replacement, but the library cannot distinguish “no games” from malformed JSON or an oversized payload. Return a readable error alongside the games and offer downloading the original stored payload for recovery. Avoid a reset action as the primary response.

### P2 — Professional game metadata and collection exchange are incomplete

`SavedGame` has no red/black player, event, round or original game date fields. PGN exports use the app's game mode as Event and generally use the export date. Import intentionally keeps only the first game from a collection. This is fine for position sharing, but insufficient for maintaining tournament records.

Preserve metadata through import → save → export. Add multi-game import with per-game outcomes, duplicate detection and a preview; add a complete backup/restore format preserving comments, branches and reviews. Acceptance should compare round-tripped content, not just legal move counts.

### P3 — Explorer replay trusts more than storage actually validates

The index's comment says moves have been validated on storage read, but normalization checks UCI syntax rather than full move legality. A damaged sequence can therefore contribute impossible positions/continuations. A validated incremental index would address both this trust gap and the performance issue below.

## Performance priorities

| Priority | Work | Evidence / limits |
| --- | --- | --- |
| 1 | Build the library position index incrementally in a worker; avoid synchronous rebuilding at startup or for metadata-only edits. | Fresh Chromium measurement: 400 games × 1,024 legal shuffling plies took **269 ms** to index, although there were only four distinct positions. This is a deliberately repetitive stress fixture, not an average user library. |
| 2 | Preserve the existing worker/SIMD/threaded architecture; measure search quality at equal time before changing defaults. | Production browser smoke reached `threaded-simd`, 8 threads on both an isolated host and simulated GitHub Pages. The board painted in 98–99 ms and engine readiness was about 1.61 s on this machine/local server. These are not mobile-network timings. |
| 3 | Offer an explicit strongest-single-line analysis preset, with multiple candidates still available for comparison. | Pikafish documents MultiPV 1 as the best-performance choice. More lines consume the same search budget. Stockfish's benchmark magnitudes should not be copied to Xiangqi. |
| 4 | Measure cold/returning NNUE transfer and caching under real hosting and limited networks. | The weights are about 53 MB. `coi-sw.js` already caches/revalidates them, contrary to older “caches nothing” comments. Do not add a second unversioned cache; check engine/network compatibility and fallback behavior on updates. |
| 5 | Split `App.tsx` by engine orchestration, review session, workspace controls and dialogs when changing those areas. | It is 7,534 lines. This is chiefly a correctness/maintainability improvement; component extraction alone is not a proven speedup. Existing engine info buffering and memoized board rendering should be retained. |

A local Node engine baseline (18-core arm64 host, threaded SIMD, four threads, 64 MB hash, depth 12, one warmup/two measured runs) gave median **1.72M nodes/s**, with 333 ms cold initialization. This is a baseline only; two multithreaded runs are not a strength comparison. Use multiple opening/middlegame/endgame positions and matched time/node budgets for engine changes.

## UI/UX and feature roadmap

Desktop (1440×1000) and phone (390×844) screenshots were inspected. The board is prominent and fits both sizes. The existing browser suite also covers keyboard navigation, flipped orientation, drag, touch actions, dialog focus, reduced motion, large text, forced colors and library actions.

The main weakness is discovering what to do, rather than lack of controls:

1. **Beginner entry path.** The default screen is Analysis with an empty graph and “No moves yet.” Put a short, dismissible first-move guide in that empty state: select a red piece, choose a highlighted point, or start a beginner opponent. Offer optional Latin/symbol pieces and a compact rule reference. Keep the full analysis workspace directly accessible.
2. **Professional study collections.** Add named studies/chapters, full metadata, bulk import/export, backup/restore and stable links from an explorer position to the games containing it. The current explorer already collects hits, but the UI only exposes aggregate continuations.
3. **Repertoire training.** Build on the existing mistake drills: hide the answer, quiz a chosen side, schedule missed positions again, track progress, and preserve alternative accepted lines. This adds a complete practice workflow rather than another evaluation display.
4. **Sourced master games and endgame lessons.** `HISTORICAL_GAMES` is deliberately empty; the removed records were not authentic. Acquire a source-attributed, legally replayable corpus and verify provenance before presenting named masters' games. Start with a small curated set, not an invented large database.
5. **Reproducible expert analysis.** Persist engine revision/network identity, threads, hash, search limits and MultiPV with analysis results. Add selected-candidate searches using UCI `searchmoves`, exportable analysis sessions, and a deliberate fresh-search/clear-hash action. Treat WDL as an engine model, not a beginner's literal personal winning probability.
6. **Mobile analysis discovery.** The mobile board is readable, but many actions move behind icons and the Analysis tab. Give first-time users concise labels/help for those controls; preserve the uncluttered board after the controls are learned.

Recommended sequence: prevent library eviction and expose recovery → shared FEN validation/cloud verdict freshness → metadata and collection backups → background indexing → beginner guide/piece choices → repertoire practice → expert analysis-session controls.

## Research references

- [Pikafish repository](https://github.com/official-pikafish/Pikafish): the Xiangqi-specific Stockfish-derived engine already used here. Retain it as the default; ordinary Stockfish is not a replacement Xiangqi backend.
- [Pikafish UCI commands](https://github.com/official-pikafish/Pikafish/wiki/UCI-%26-Commands): engine options, MultiPV tradeoffs and game/search lifecycle. Use the shipped engine's advertised options as the final authority.
- [Stockfish FAQ](https://official-stockfish.github.io/docs/stockfish-wiki/Stockfish-FAQ.html) and [benchmark data](https://official-stockfish.github.io/docs/stockfish-wiki/Useful-data.html): useful methodology for hash/MultiPV/search tradeoffs; chess-specific ratings and calibration do not transfer directly.
- [Fairy-Stockfish WASM](https://github.com/fairy-stockfish/fairy-stockfish.wasm): relevant reference for browser variant-engine integration, not evidence that changing engines would improve this app.
- [PyChess repository](https://github.com/gbtami/pychess-variants) and [features](https://www.pychess.org/features): a useful product comparison for puzzles, PGN exchange, piece sets, themes and local/server analysis.
- [Lichess analysis source](https://github.com/lichess-org/lila/tree/master/ui/analyse): reference implementation to investigate for analysis workspace separation and study interaction patterns.

```sh
npm run dev -- --host 127.0.0.1
# In another terminal:
node scripts/test-audit-browser.cjs
node scripts/bench-library-browser.cjs
```

Both accept `XIANGQI_QA_URL` for an existing dev/preview server. The benchmark asserts reuse of search text; elapsed times are diagnostic rather than hardware-dependent pass/fail gates. The focused gate uses a blocked cloud route and never needs a live cloud response.

Local screenshots and engine measurements are in `.cache/audit-2026-09-05/` (ignored by Git). Browser checks here used Chromium; real Safari/iOS, Firefox, low-memory phones and constrained networks remain unverified. The WASM toolchain was not rebuilt because these changes do not alter engine sources or artifacts.
