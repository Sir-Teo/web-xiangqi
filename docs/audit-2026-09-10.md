# Interaction responsiveness — September 10, 2026

The September 9 passes asked whether the layout *fits*. This one asks a
different question of the same app: when a reader touches it, how long before it
answers. Nothing here is about where a box lands. It is about the main thread —
what holds it, for how long, and whether that time lands on an interaction or on
time the reader could not have used anyway.

The instrument is the `long-animation-frame` API, which reports a frame's
`blockingDuration` **and** attributes the scripts inside it: function name,
source file, and the invoker that started it. That attribution is what made the
one real defect findable — it named the function, in the file, under
`DOMWindow.onpointerdown` — rather than leaving a slow frame to be guessed at.
CPU throttling came from CDP (`Emulation.setCPUThrottlingRate`); 4x stands in
for a mid-range phone and 6x for a slow one. Every number below was re-measured
on the production bundle, because a dev build's React is several times slower
than the one a reader gets.

## Bugs fixed

| Commit | Finding and user impact | Change and evidence |
| --- | --- | --- |
| `24575ac` | Sound is on by default, and unlocking it meant calling `new AudioContext()` from the `pointerdown` listener that arms it. That constructor starts the audio device — and that cost is **flat across throttle rates**, ~125ms at 1x, 4x and 6x alike, because it is device startup rather than script. A fast machine does not escape it. So every visit spent it on the reader's very first tap: measured against Flip board, a click that does almost nothing else, the frame answering that first tap ran **131ms unthrottled and 186ms at 4x**, with 79ms and 132ms of it blocking, against **0ms for every tap after it**. It is the one interaction a reader judges an app by, and the one INP measures. | Build the context at idle; the gesture is left with `resume()`, which measures under a millisecond. First tap now blocks for **0ms**. Verified under `--autoplay-policy=document-user-activation-required`, where the idle-built context is `suspended` until the tap resumes it to `running` — so the autoplay contract is unchanged. `unlockSoundEffects` still builds one if the idle callback has not run, so this is never worse than before, only usually free. |
| `9d94f6b` | The eval graph's tooltip is placed from its own rendered box, so the box is measured — but it was measured in a layout effect keyed on the point, and `points` is rebuilt from `currentEval`, so a streaming engine hands it a new point several times a second. Each read took geometry straight after React had mutated the DOM, forcing a layout, for a box that barely ever changes: across a load it takes **two sizes, 96x48 and 103x48, in seven measurements**; one move step measured five times for the same two; four seconds of live analysis measured once more for no change at all. | Measure once, synchronously, when the tooltip appears — needed before the first paint, or the box lands where the 150x52 default put it — and let a `ResizeObserver` report the rest, reading the box out of the layout the browser already does. ## What the second fix is actually worth

Recorded plainly because the attributed number and the saved number are not the
same, and the difference is the interesting part.

`getBoundingClientRect` on the tooltip was *attributed* 96ms of synchronous
layout on a cold load, 127ms with a game in the URL, and 14ms per move step at
4x. Almost none of that is saved. Most of those reads were cheap follow-ons: the
move list flushes layout first on the same interaction — `centreActiveMove` has
to, since centring the active row means knowing where it is — and a read after
that returns from a clean layout for nothing.

Interleaved three rounds against the unfixed build, ten move steps on a 390x844
phone at 6x with an 80-ply game:

| | forced reads | time | tooltip's own reads |
| --- | ---: | ---: | ---: |
| before | 72 | 36ms | 12 |
| after | 60 | 32ms | 0 |

Consistent in every round, and about 13% — real, and much smaller than 96ms.
Cold-load FCP and total blocking time did not move at all; that layout was
happening either way. The change is worth having for what it removes rather than
for what it saves, and the regression that guards it is red both ways.

## The cost the first fix moves rather than removes

The audio device has to start somewhere before the first sound. Moving it to
idle does not delete ~125ms of blocked main thread, it relocates it, and the
honest accounting is that a lab metric gets worse:

| production, 4x, interleaved 3 rounds x 5 samples | main | branch |
| --- | ---: | ---: |
| first contentful paint | 255ms | 255ms |
| engine reports ready | 1358ms | 1367ms |
| total blocking time | 118ms | 189ms |

FCP unchanged, engine-ready unchanged within noise, and **TBT up 64ms**. The
idle callback fires around 257ms in, so the long task lands squarely inside the
load trace. It was left there deliberately: the engine is still booting until
~1358ms, so the app is not usable at 257ms whatever happens on the main thread,
and no reader has tapped by then. Delaying the prime to ~1500ms would clear the
trace window and put the task exactly where the app *becomes* usable, which is
worse for the reader and better only for the metric. Recorded so the next pass
does not "fix" the TBT number.

## Second round — the heavy states

The sweeps above all ran on an ordinary game. This round asked the same question
of the states a long-lived install actually reaches, and found nothing to fix.

**A held arrow key.** The interesting failure here is not a slow frame, it is a
backlog: if a step costs more than the auto-repeat interval, presses queue and
the board keeps moving after the reader lets go. It does not. Thirty presses at
10, 20 and 33Hz on an 80-ply game at 6x: **30 of 30 land at every rate, drift
after release is zero**, blocking is zero, frames stay at a 17ms median with a
33–37ms p95 — a slight stutter under fast repeat on a slow phone, no queue.

**A large saved library.** Search re-filters the whole library on every
keystroke, so the question is whether it scales. It does not need to: measured
from keydown to the next paint, at 6x,

| saved games | payload | median | p95 | max |
| ---: | ---: | ---: | ---: | ---: |
| 200 | 88KB | 3ms | 59ms | 59ms |
| 1,000 | 444KB | 4ms | 86ms | 86ms |
| 3,000 | 1.3MB | 4ms | 89ms | 89ms |
| 6,000 | 2.7MB | 4ms | 88ms | 88ms |

Flat from a thousand games on, and the median keystroke is 3–4ms at every size.
Opening the tab, scrolling the list and loading a game were all 0ms blocking at
400 games.

**A deep variation tree.** 229 nodes off a 40-ply main line, built with the app's
own move generator so every branch is legal, and loaded through `?tree=` — which
caps at 8,000 JSON characters, so this is very near the largest tree a share link
can carry. At 4x: 16ms blocking over eight forward steps, worst frame 71ms,
everything else at zero. At 6x: 53ms over eight steps, worst frame 101ms, and
scrolling the tree panel stayed at a 17ms median. One frame in six slots is a
visible hitch on a slow phone, and it is the largest number this pass produced.

**What that hitch is.** The same minified function tops the worst frame in move
navigation, library search and breadcrumb clicks, which looked like a shared hot
path worth naming. It is not: `_n` in the bundle is React's own
`dispatchDiscreteEvent` — the synchronous render the click triggers. There is no
app-level hotspot behind it, so shrinking it means shrinking what re-renders on
a move change, across a 7,853-line `App.tsx`. That is a real piece of work for a
frame that is only visible at 6x, and it was left alone rather than started
badly.

**Conditions changing under the app.** A phone rotated portrait to landscape and
back, four times and then six times rapidly; `prefers-color-scheme` flipped dark
and light; `prefers-reduced-motion` set to reduce. Every settle: the board keeps
its 9:10, all ninety intersections stay hit-testable, no horizontal overflow, the
whole board inside the viewport, and **0ms blocking on every transition**. Nothing
was left stuck by the rapid rotations, and under reduce, zero elements still
carry a transition or animation over 1ms.

**The engine boot window.** Between first paint and a usable engine there is over
a second where the app could look ready and not be. It does not: the board is up
and interactive at 278ms, the state line reads "Loading engine" and then counts
the download out in megabytes — 2, 8, 14, 21, 28, 34, 40, 46 — before moving to
"Engine ready", "Queued", "Analyzing", and the first evaluation at 2.2s. The
board's own eval chip stays empty until there is a real number rather than
showing a zero.

## Two traps worth writing down

**Playwright's page evaluations grant the document user activation.**
`page.evaluate`, `waitForFunction` and `waitForSelector` polling all run script
with activation, so anything autoplay-gated behaves as if the reader had already
interacted: a context built before any of them is `suspended`, one built after
is `running`. A first draft of the sound regression asserted `suspended` and was
reading the harness, not the app. The fix is to assert the *call* — wrap
`resume` on the prototype and count it — and to force the precondition rather
than assume it. Only Node-side `page.waitForTimeout` grants nothing.

**A cost that is flat across throttle rates is not script.** `new
AudioContext()` measured 124–130ms at 1x, 4x and 6x. Anything with that shape is
device or I/O work; no code tuning will shrink it, and the only move available
is to take it off the interaction path.

## Verification and limits

`npm run test:ui:layout`, `npm run test:ui:audit`, typecheck, lint and 94 test
files / 1,091 unit tests all pass; lint keeps the one pre-existing unnecessary-memo-dependency warning in
`LibraryPanel`. Both fixes carry a regression in `scripts/test-ui-layout.cjs`,
and both were confirmed red against the unfixed code before being kept — the
eval graph one twice over, since a variant that keeps the mount measurement but
drops the observer puts the tooltip 3.28px inside the y-axis gutter, exactly
half the difference between the two widths.

Limits. Chromium only, headless, on one machine; a CPU throttle is not a phone,
and the audio-device timing in particular is this machine's sound hardware. The
A/B methodology matters more than usual here: two runs of the *same* bundle
differed by 25ms of median FCP, so every comparison above is interleaved
main/branch within each round, at least five samples a side, with the served
bundle hash checked to confirm the swap landed. Real INP was not collected from
real users; every number is a lab number. No engine, rules, storage or import
path was changed, and no engine binary was rebuilt.
