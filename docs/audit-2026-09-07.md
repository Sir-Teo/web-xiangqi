# Xiangqi audit and improvements — September 7, 2026

The next major product investment should be professional study records and training workflows. The app already has a capable Xiangqi engine, variations, annotations, review, drills, cloud continuations, backup/recovery, and substantial keyboard support. A different engine or more toolbar controls would not address its biggest remaining gaps.

This pass examined rules and position replay, library validation and persistence, autosave, import/export, engine scheduling and configuration, WASM build settings, service-worker delivery, the board and analysis workspace, responsive behavior, and CI. It revisited the September 5 audit rather than treating its resolved findings as new bugs. Generated engine binaries were exercised through contract, smoke, parity, and production-browser checks; they were not rebuilt or audited instruction by instruction. This is not a claim that every possible interaction or every line is proven correct.

## Measured performance

A deliberately repetitive stress library of **400 games × 1,024 legal plies** was tested in local Chromium:

| Path | Elapsed time | UI consequence |
| --- | ---: | --- |
| Synchronous index with move validation | 716 ms | Replay occupies the main thread. |
| Worker index with the same validation | 876 ms wall time | Browser rendered 54 frames while indexing. |

The win is responsiveness, not faster computation or higher engine NPS. Worker startup and structured cloning add overhead. These are single-run diagnostic measurements on this machine, not a mobile benchmark or a universal latency guarantee. Reproduce with `scripts/bench-explorer-browser.cjs` against a dev server.

Production smoke after the worker/guide/cache changes reached **threaded-simd with 8 threads** on both an isolated host and simulated GitHub Pages. In that run the board appeared in 159–165 ms and engine readiness was 1.67–2.25 seconds; a legacy-worker upgrade also passed. These local-server timings do not predict a cold mobile download.

## Biggest remaining performance opportunities

1. **Incremental indexing and asynchronous library storage.** The new worker still rebuilds when the library array changes, including a rename. Cache validated paths by start position plus moves, update metadata without replay, and reuse unchanged games. Separately profile `loadLibraryState` normalization and serialization near the 3,000,000-character/500-game limits; they remain synchronous. An IndexedDB migration needs transactional writes, recovery, migration tests, and backup compatibility. Do not merely raise those limits.
2. **Versioned engine assets and network delivery.** The roughly 53 MB NNUE transfer dominates a cold visit. Keep conditional caching; introduce a build manifest binding core, wrapper, and network identities before offering offline mode. Measure constrained-network boot, returning visits, failed updates, and memory use on real phones. Removing stale fallback fixes one failure path but does not make independent asset requests atomic.
3. **Single-line strength versus candidate comparison.** The app already uses MultiPV 1 outside the Engine detail panel and has a candidate-count control. Make the cost clear beside that control; retain multiple lines for comparison. Both [Pikafish's UCI documentation](https://github.com/official-pikafish/Pikafish/wiki/UCI-%26-Commands) and [Stockfish's FAQ](https://official-stockfish.github.io/docs/stockfish-wiki/Stockfish-FAQ.html) recommend one line for the strongest best-move search at a fixed budget. No numeric Stockfish strength gain should be assumed for Xiangqi.
4. **Measure engine settings rather than increasing them blindly.** SIMD, worker isolation, and bounded thread/hash configuration already exist. The shipped pthread pool and WASM memory ceiling constrain safe settings. Compare equal-time searches across openings, tactical middlegames, and endings on desktop and mobile; nodes/second alone is not playing strength.
5. **Separate App responsibilities when changing them.** App.tsx remains about 7,700 lines and coordinates engine search, reviews, persistence, dialogs, and workspace state. Extract review sessions, game lifecycle, and dialogs behind explicit interfaces. This primarily reduces race and maintenance risk; extraction alone is not an established speedup. Preserve existing engine-info buffering and memoized board behavior.

## UI/UX assessment

The board is prominent, pieces and move feedback are clear, and the existing app has useful keyboard navigation, drag, markers, accessible panel tabs, legal-move explanations, and mobile actions. The broad layout suite exercised those paths along with dialog focus, reduced-motion scrolling, review actions, import errors, and storage failures. Screenshots were visually checked, not only measured through DOM boxes.

The guide addresses first-action discovery without consuming the desktop board area. On a 320×568 phone it collapses to a help row; on larger phones its controls fit above the board. It is hidden after play begins and in Pro mode. A beginner still needs a short interactive rules course and a few verified tactical/endgame lessons. The labels “Master” and “Full strength” should not be presented as validated human Elo ratings.

For advanced users, prioritize records and navigation over more buttons. A study should retain who played, where it came from, why a line was chosen, and which engine/settings produced its analysis. WDL is an engine outcome model, not an individualized forecast of a beginner's chances. The empty historical-game corpus is intentional: do not fill it with unattributed or invented master games.

- [PyChess](https://github.com/gbtami/pychess-variants) and its [feature list](https://www.pychess.org/features): comparison for puzzles, local/server analysis, PGN exchange, localization, and piece/theme choices.
- [Sibling web-chess learning plan](https://github.com/Sir-Teo/web-chess/blob/main/docs/cross-app-learning-plan.md): useful context for shared review, library, and workspace concerns; recommendations here were checked against this repository's current implementation.

## September 8 continuation — open matching studies

The explorer now lists up to eight matching saved games, newest saves first, with one first occurrence per game. Opening a match selects that ply while preserving the complete line, the saved main-branch choice, other variations, and notes. An earlier position does not inherit the saved final result as a current game-over state. Custom Black-to-move roots retain their move counters. An invalid game is rejected without changing the board and offers library access for backup.

The browser regression exposed a separate note-editor issue: node IDs restart on game load, but the draft previously depended only on that ID. Loading a different game at the same ID could retain the previous draft. Drafts now carry a game identity; switching games loads the new note and cancels the old pending write. This identity is stable during normal engine updates and note editing.

The worker still retains the full index. Only eight occurrence records are transferred with the current report, so this feature does not undo the background-indexing change. `test-library-matches-browser.cjs`, included in `test:ui:audit`, covers desktop/mobile navigation, invalid-game rejection, second-branch preservation, notes, and custom-root counters. The additional unit test covers deduplication, ordering, and bounded selection; the suite now has 1,067 tests. Tournament metadata, collection import, chapters, and repertoire scheduling remain open priorities.


## September 8 continuation — tournament metadata

PGN import now reads the leading game's Red/White, Black, Event, Site, Date, and Round tags. Players can edit these in a collapsed Game details section beside the move notes. Dates remain text so partially unknown historical dates such as `2020.??.??` survive. Escaped quotes and backslashes round-trip, and fields are normalized and bounded to 256 characters at storage/export boundaries.

Metadata remains separate from the library's study label. Saved cards show players and tournament details, and library search includes those fields. Current-game PGN export, saved-game PGN export, library backups, and autosave recovery retain them. Loading a headerless game or starting a new root clears the previous game's metadata; continuing/practicing the current line retains it.

## September 8 continuation — PGN collections and saved-note export

The library now accepts a collection file through a preview with per-game selection. Parsing and legal-move replay run in a dedicated worker, with cancellation, a timeout, and stale-request guards. Each main-line and variation move is validated from its own position, including custom Black-to-move FEN roots. Unrecognized movetext, broken comments/variations, and conflicting result markers reject the collection before any write. Game boundaries respect quoted headers and comments and work even when multiple games share one physical line.

The selected games append in one storage write, re-reading the current library at confirmation. Invalid batches, unreadable existing data, capacity overflow, and quota failures preserve the existing library. The preview does not change the board. Re-importing the same file creates new copies; the preview states this explicitly. Limits are 1,000,000 characters per collection, 500 games per library, 1,024 moves including variations per game, and the existing bounded field/note sizes. This is coordinate PGN support, not WXF/Chinese notation collection parsing. Unsupported tags are not retained; annotation glyphs and engine commands are retained as note text, not reconstructed review scores. Notes preceding the first move are rejected rather than silently dropped.

Browser QA found an independent export bug: converting a saved tree to export nodes discarded `comment`. Commit `ceeaa56` fixes it for main-line and variation notes; its regression checks the actual downloaded PGN. Atomic collection writes landed separately in `944c831`.

The parser uses the token, comment, recursive-variation, and game-termination distinctions in the [PGN specification coordinated by Steven J. Edwards](https://www.saremba.de/chessgml/standards/pgn/pgn-complete.htm). This app substitutes Xiangqi coordinate moves for orthodox chess SAN. Tests cover inline games, quoted braces, semicolon comments, nested branches, malformed records, size limits, custom starts, and illegal moves. Desktop/390px browser tests cover worker preview, selection, save failures, unchanged board state, and exported metadata/branch notes. These tests are included in `test:ui:audit`.

`npm run verify` passed with 94 files / 1,091 tests and the existing LibraryPanel lint warning. No engine source was changed; the local WASM build was regenerated during validation. Collection processing was also exercised against the bundled production worker. Incremental indexing/storage, broader notation/annotation interoperability, study chapters, and repertoire scheduling remain open priorities.

A follow-up phone check found a 200-character filename overflowing the preview despite the page itself having no horizontal scrollbar. The filename now wraps, and the browser regression checks the panel’s scroll width as well as the document’s.
