Deletion snapshots now also check game identity. Previously, loading another
game with the same starting FEN left the old Undo action available; browser QA
confirmed that clicking it replaced the newly loaded board with the previous
study. Undo now clears on load/reset and the restore operation itself rejects
snapshots from another game. Desktop/phone checks preserve ordinary deletion
recovery and cover both same-root library loads and New Game.

Autosave now checks the recovery reader's move and tree limits before reporting
success. A 1,025-move snapshot previously returned `saved` while its own reader
returned `null`; the 2 MB byte ceiling did not catch a record of only 7,289 JSON
characters. Oversized studies now show the existing recovery warning and PGN
download action. Invalid snapshots are also rejected before writing. Tests cover
the exact limit, branches outside the current line, and returning to recoverable
size after pruning. Larger study capacity remains an open product requirement.

The recovery warning's phone actions were below the 44-pixel touch target and
the portrait warning overlapped the move-navigation strip. Recovery and Undo
actions now have 44-pixel minimum touch dimensions, and portrait recovery
warnings clear the strip. Browser checks measure action bounds and the gap,
verify no horizontal overflow at 320/390 pixels, and complete the recovery flow.

The serializer now uses an explicit traversal stack and one ancestry set instead
of copying the whole ancestor path at every move. Shared subtrees still appear
under every branch; existing cycle behavior, child ordering, normalized notes,
and immutable inputs are retained. A 10,000-node helper stress test no longer
exhausts the call stack. This does not raise the app's 1,024-move storage limit.

## Performance findings

- **Avoid wasted searches first.** The confirmed scheduling race is fixed.
  Continue examining search ownership and stop/restart boundaries before changing
  engine budgets. Preserve the full move history when analyzing repetitions.
- **Avoid repeated tree copies.** On this development machine, adding 64 moves
  to an 800-move tree took a median 4.73 ms (p95 5.11 ms) with the old insertion
  algorithm versus 0.25 ms (p95 0.30 ms) with the shared helper. The benchmark
  warmed both implementations, interleaved 50 runs, and checked equal output.
  This isolated Node/Vite JavaScript measurement excludes rendering, engine
  search, and storage; it is not a whole-interaction or phone speed claim.
- **Serialize ancestry once.** Run `node scripts/bench-study-serialization.mjs`
  to compare the former algorithm with the current serializer. On this machine,
  a 1,024-move annotated chain changed from a 1.758 ms median / 2.229 ms p95 to
  0.096 ms / 0.154 ms. The 50 interleaved samples follow warmup and an equal-output
  check. This excludes JSON encoding, storage writes, browser rendering, and
  engine work. The performance gain is in assembling the tree snapshot.
- **MultiPV costs depth.** [Stockfish's UCI documentation][uci] recommends one
  line for maximum performance. The pinned Pikafish `search.cpp` performs a root
  search for each PV. The app already uses one line outside detailed analysis;
  increasing defaults would trade depth for alternatives. Benchmark fixed-time
  depth and responsiveness with 1/3/5 lines before changing the existing choice.
- **Coalesce progress before crossing the worker boundary.** The real network
  download produced a median 4,085 callbacks versus 52 after coalescing, about
  98.7% fewer messages. Five interleaved Chromium samples per implementation used
  fresh contexts, the real 53,719,310-byte network, single-SIMD, one thread, and
  16 MB hash; each completed a depth-one search. Median ready times were 935.1
  and 931.1 ms, effectively unchanged in this small local experiment. This is
  a reduction in queued work, not evidence of faster engine search, rendering,
  or phone startup. Initial/completion/reset reports and byte integrity remain
  covered, including unknown and encoded content lengths. Reproduce with
  `git show 8600929:templates/pikafish.js > /tmp/xiangqi-progress-baseline.js`
  followed by `node scripts/bench-progress-browser.cjs /tmp/xiangqi-progress-baseline.js`.
- **Ordinary compression will not shrink the weights.** The shipped NNUE file
  is 53,719,310 bytes. Node gzip produces 53,732,472 bytes; Brotli quality 4
  produces 53,719,450. Both are slightly larger. Prioritize reliable versioned
  reuse of matching engine/network assets, and investigate smaller compatible
  networks only with strength and parity validation.
- **Frontend structure remains worth investigating.** The production main
  JavaScript bundle is about 473 kB / 145 kB gzip. Splitting optional study and
  import surfaces could reduce first-load parsing and simplify maintenance.
  The large source file is evidence of complexity, not proof of slow frames.
  Use production traces before claiming a speed improvement.
- **Device behavior still needs direct evidence.** Chromium viewport tests
  verify layout, not phone thermal throttling, memory pressure, touch hardware,
  Safari, or battery drain. Do not tune mobile thread/hash defaults from desktop
  viewport emulation alone.

## Feature priorities

1. **Analyze selected candidates.** Let a player compare specific legal moves
   using `go ... searchmoves ...`. Both the pinned Pikafish parser and upstream
   support this; the option must come last in the pinned parser. Label restricted
   analysis clearly, preserve its candidate set in the search identity, and avoid
   presenting its score as the unrestricted position evaluation. A
   [Stockfish maintainer explains][searchmoves] why a restricted search may score
   differently. This is a useful pro feature with an approachable beginner
   question: “What about this move?”
2. **Persist useful analysis as study variations.** Keep chosen engine lines,
   evaluations, depth, and notes so opening preparation survives a navigation or
   reload. The existing move tree, comments, and PGN import/export are a strong
   base. Keeping the move continuation is now implemented with duplicate and
   persistence coverage. Evaluation/depth provenance and richer study metadata
   remain future work.
3. **Guided tactical lessons and spaced mistake practice.** The app already
   has first-move help, letter pieces, an opponent ladder, and review-based
   mistake drills. Add curated lessons for horse legs, cannon screens,
   flying generals, and stalemate losses, plus progress across practice sessions.
   [PyChess][pychess] provides a useful reference for the combination of puzzles,
   analysis, editor, import/export, and multilingual learning.
4. **Larger study libraries.** Storage currently caps the library at 500 games
   and 3,000,000 JSON characters. A professional preparation corpus will exceed
   these limits. Plan an IndexedDB migration with atomic writes, metadata
   indexing, incremental explorer updates, and recoverable backups; simply
   raising the synchronous localStorage limits would increase stalls and quota
   failures.
5. **Chinese interface localization.** Chinese notation is implemented; an
   English-only interface still creates friction for many Xiangqi players.
   Extract product strings with native-language review and verify longer labels,
   narrow screens, focus order, and screen-reader announcements.

Pikafish is already a [Stockfish-derived Xiangqi engine][pikafish]. Ordinary
Stockfish is a protocol and architecture reference here, not a replacement
engine. Upstream findings must be checked against the pinned local revision
`beeca5cc785ceb2026c5f9248f6e057573b12906` before being used in the shipped WASM.
