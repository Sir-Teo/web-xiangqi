## Performance findings

- **Avoid wasted searches first.** The confirmed scheduling race is fixed.
  Continue examining search ownership and stop/restart boundaries before changing
  engine budgets. Preserve the full move history when analyzing repetitions.
- **MultiPV costs depth.** [Stockfish's UCI documentation][uci] recommends one
  line for maximum performance. The pinned Pikafish `search.cpp` performs a root
  search for each PV. The app already uses one line outside detailed analysis;
  increasing defaults would trade depth for alternatives. Benchmark fixed-time
  depth and responsiveness with 1/3/5 lines before changing the existing choice.
- **Ordinary compression will not shrink the weights.** The shipped NNUE file
  is 53,719,310 bytes. Node gzip produces 53,732,472 bytes; Brotli quality 4
  produces 53,719,450. Both are slightly larger. Prioritize reliable versioned
  reuse of matching engine/network assets, and investigate smaller compatible
  networks only with strength and parity validation.
- **Frontend structure remains worth investigating.** The production main
  JavaScript bundle is about 473 kB / 145 kB gzip. Splitting optional study and
  import surfaces could reduce first-load parsing and simplify maintenance.
  The large source file is evidence of complexity, not proof of slow frames.
  Use production traces before claiming a speed improvement.
- **Device behavior still needs direct evidence.** Chromium viewport tests
  verify layout, not phone thermal throttling, memory pressure, touch hardware,
  Safari, or battery drain. Do not tune mobile thread/hash defaults from desktop
  viewport emulation alone.

## Feature priorities

1. **Analyze selected candidates.** Let a player compare specific legal moves
   using `go ... searchmoves ...`. Both the pinned Pikafish parser and upstream
   support this; the option must come last in the pinned parser. Label restricted
   analysis clearly, preserve its candidate set in the search identity, and avoid
   presenting its score as the unrestricted position evaluation. A
   [Stockfish maintainer explains][searchmoves] why a restricted search may score
   differently. This is a useful pro feature with an approachable beginner
   question: “What about this move?”
2. **Persist useful analysis as study variations.** Keep chosen engine lines,
   evaluations, depth, and notes so opening preparation survives a navigation or
   reload. The existing move tree, comments, and PGN import/export are a strong
   base; audit provenance and duplicate-line behavior before adding controls.
3. **Guided tactical lessons and spaced mistake practice.** The app already
   has first-move help, letter pieces, an opponent ladder, and review-based
   mistake drills. Add curated lessons for horse legs, cannon screens,
   flying generals, and stalemate losses, plus progress across practice sessions.
   [PyChess][pychess] provides a useful reference for the combination of puzzles,
   analysis, editor, import/export, and multilingual learning.
4. **Larger study libraries.** Storage currently caps the library at 500 games
   and 3,000,000 JSON characters. A professional preparation corpus will exceed
   these limits. Plan an IndexedDB migration with atomic writes, metadata
   indexing, incremental explorer updates, and recoverable backups; simply
   raising the synchronous localStorage limits would increase stalls and quota
   failures.
5. **Chinese interface localization.** Chinese notation is implemented; an
   English-only interface still creates friction for many Xiangqi players.
   Extract product strings with native-language review and verify longer labels,
   narrow screens, focus order, and screen-reader announcements.

Pikafish is already a [Stockfish-derived Xiangqi engine][pikafish]. Ordinary
Stockfish is a protocol and architecture reference here, not a replacement
engine. Upstream findings must be checked against the pinned local revision
`beeca5cc785ceb2026c5f9248f6e057573b12906` before being used in the shipped WASM.

## Scope and verification

Inspected this pass: repository/build/test inventory, architecture and prior
audit findings, engine initialization and search queue, cloud book/line/rule
hooks, library explorer worker boundary, board input structure, application
analysis wiring and PV controls, beginner entry flow, and CI/asset configuration.

opening/library checks, engine contract, smoke/parity, and production build.

focused browser audit, full UI layout suite, and production smoke also pass. Browser checks
use Chromium on macOS. Production smoke exercises isolation headers, a
Pages-style host isolated by `coi-sw.js`, and legacy service-worker recovery.
One initial broad layout run was invalidated by live source edits adding hooks;
its Vite hot reload produced a React hook-order error. The suite was restarted
with application source held fixed. Do not edit application files while running
long suites against the development server.
