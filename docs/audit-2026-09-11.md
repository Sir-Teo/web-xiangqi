## Review cancellation and annotation ownership

A browser regression demonstrated that even a scoreless review erased a
`$4` quality mark on an imported sibling variation. Starting review cleared
all qualities globally; successful intermediate searches also wrote scores and
recommendations into the study, so cancellation left a partial review behind.
Review now stages scores and recommended lines privately, applying them together
only on completion. Cancelling, a scoreless result, or worker failure discards
those staged results. A rerun retains the previous completed summary for saving
and autosave, and cancellation restores that summary in the review panel.
Clearing a completed review touches only its reviewed line, and clears its full
recommended line along with its best move. Sibling annotations remain intact.
The running panel explains when scores change and what Cancel preserves.

This also removes per-position recommendation writes and the timed score batch
writes that repeatedly copied the move tree and invalidated storage snapshots.
This is a reduction in application work, not a measured engine speedup. Review
progress still updates per position; the driver explicitly observes completed
steps so an immediately returning engine cannot stall the queue when React
batches searching and idle into one render.

## Live score comparisons and remaining score-type work

The pinned [Pikafish score formatter](https://github.com/official-pikafish/Pikafish/blob/beeca5cc785ceb2026c5f9248f6e057573b12906/src/uci.cpp)
outputs separate `cp` and `mate` kinds; the [Stockfish UCI reference][uci]
also demonstrates typed scores, bounds, and sequential MultiPV updates. The
live line score badges already kept the kind, but the comparison labels inferred
it from the numeric mate-sentinel range. Thus `cp 29950` could be labelled
"Mate in 50", despite its badge displaying a centipawn evaluation. A unit
regression additionally reproduced losing mate zero labelled "Mate in 0".
Comparisons now read the engine's score kind, retain negative zero, and avoid
subtracting a mate sentinel from an ordinary score. A secondary reading above
the current first line says "ahead" instead of "Equal"; a comparison involving
a bound says "Not exact" with explanatory hover text. These are live readings,
not claims that all slots have finished the same search depth.

A controlled browser workflow checks both sides to move, Red-perspective score
badges, spoken line descriptions, bounds, and layout at 1440/390/320 pixels.
It is part of the three-browser regression matrix.

The same ambiguity also corrupted persisted annotations: a direct reproduction
imported `[%eval 200.00]` as `20000`, displayed `+M10000`, and exported
`[%eval #10000]`. Move evaluations now retain a score-kind override wherever a
centipawn value overlaps the legacy mate range. This sparse representation
preserves the existing encoding for other values and avoids adding redundant
metadata to every ordinary move. The override travels through PGN main lines
and variations, storage/share normalization, engine completion, review annotations
and key moments (including their root-position evaluation), graph points/extrema,
library summaries, and PGN export. Replacing an evaluation replaces its kind even
when the numeric value is identical. A rejected engine bound cannot change the
kind of the exact score being retained.

Unit checks cover normalization, same-number kind replacement, root and move
review kinds, and a mixed cp/mate PGN → storage → share → PGN round-trip.
The browser workflow also checks graph and library labels, completed review
labels, reload recovery, share loading, and same-number live-engine replacement
at all three widths. Existing records that already lost their score kind retain
their legacy interpretation; the original PGN must be reimported or the position
reanalyzed to recover the intended type. No threshold change or clamping of
large imported numeric evaluations is used to hide that ambiguity.

## Graph peak score ordering

Graph peak selection now compares evaluation types before numeric magnitudes.
Previously, +400.00 pawns outranked a forced mate, and +200.00 could win a tie
against +M10000 because both use the stored number 20000. Forced Red mates
rank above finite pawn evaluations; forced Black mates rank below them, with
mate distance breaking ties within either mate category. This follows the
[python-chess score ordering](https://python-chess.readthedocs.io/en/stable/engine.html#chess.engine.Score).
Regression coverage includes both colors, mate zero, overlapping stored values,
large live centipawn readings, and excluding unselected variations from peaks.
The plot remains capped at ±12 pawns; its existing Swing value measures the
clamped plotted span rather than a numeric difference between mate sentinels.

## Position editor keyboard navigation

The editor exposed all 90 squares as separate Tab stops and did not move
between them with arrow keys. It now has one board Tab stop, arrow navigation,
Home/End for the current rank, and Ctrl+Home/End for the board's corners.
Native Enter/Space activation places or removes a piece once. Grid, row, and
cell semantics plus a short keyboard instruction describe the interaction.
This follows the [W3C keyboard convention](https://www.w3.org/WAI/ARIA/apg/practices/keyboard-interface/)
of using Tab between components and arrows within a composite component.

The shared dialog trap now excludes negative Tab indices, disabled/inert
controls, and descendants of hidden containers; it includes native disclosure
summaries. Wrapping focus lets the dialog scroll to the destination. The
regression checks editing, boundaries, returning focus after Escape, hidden
controls, and visible focus at desktop, phone, short, and landscape sizes.
This is automated browser coverage, not a complete assistive-technology audit.
The committed editor passes at 1440×900, 390×844, 320×640, and 844×390 in
Chromium, Firefox, and WebKit. On macOS, the WebKit harness uses Option-Tab
for the full control sequence: plain Tab skips buttons with the default
browser preference, as described in [Apple's keyboard shortcuts](https://support.apple.com/en-gb/guide/safari/cpsh003/mac).

## Performance findings

The board now receives stable absent values for hidden arrows and highlights.
A controlled Chromium development run with ten distinct visible engine scores
recorded twelve renders of the unchanged board; React's commit hook identified
only `highlights` and `arrows` as changed props. Empty arrays were being recreated
despite the master visibility switch being off. The same workflow now records
zero board renders, while all ten engine readings still appear. Production
Chromium, WebKit, and Firefox pass at 1440 and 390 pixels, including hiding and
restoring a user marker and the arrows. This is avoided UI work, not measured
engine throughput or a physical-device timing claim. The regression uses the
React 18 DevTools commit hook and work flag; it must be revisited on a React
major-version migration.

The default view with arrows visible had the same problem: ten distinct score
updates caused ten board renders although the arrow geometry was unchanged.
A per-board, one-result selector now reuses the drawing array when its complete
serialized drawing data is identical. The same desktop and phone workflow now
records zero unchanged-board renders in all three browsers, with every engine
score still updating. Changing the recommended move redraws the arrow; unit
coverage also checks endpoints, colors, opacity, width, kind, paint order,
spotlighting, independent boards, and preservation of previous results.
This follows the rendering principle in
[Chessground's SVG implementation](https://github.com/lichess-org/chessground/blob/master/src/svg.ts),
which compares drawing hashes before synchronizing its SVG. The local change
reuses React props; no engine search settings or budgets change.

The library explorer now reuses its worker across saved-library changes and
keeps only the newest pending query while an index build or lookup is running.
Previously, every new library array terminated and replaced the worker. A
controlled browser test holding the first reply measured 21 workers and 21
build requests for 21 library versions before the change, versus one worker
and two builds after it. These are work counts, not a wall-clock speedup claim.
The same replacement path produced a WebKit development-server module-load
error after saving a game; tracing identified the index worker, and the native
WebKit reproduction passes with worker reuse.

Replies carry request IDs so old or duplicate replies cannot finish a newer
query. Clearing the library releases the existing index; empty startup creates
no worker. Failure remains visible without damaging saved games, and a later
library update can start a replacement. Controlled coverage checks coalescing,
stale replies, emptying/repopulating, and abandoned-worker errors at 1440, 390,
and 320 pixels. Native-worker coverage verifies legal continuations and board
navigation before index loading completes. Both workflows are included in the
Chromium, WebKit, and Firefox matrix.

- **Bound DhtmlXQ tag scanning.** Repeated unclosed movelist or comment tags
  below the 200,000-character import limit made lazy regexes rescan each
  suffix. The reader now finds fixed tag boundaries directly and indexes
  numbered comment closers once, advancing each cursor monotonically. It
  preserves case handling, Unicode offsets, duplicate comments, exact numeric
  spellings, and outer-first, non-overlapping matches; 150 fragmented tag
  streams are checked against the old matcher. In an isolated local Node/Vite
  run with three warmups and ten samples, the 198,000-character movelist case
  fell from 278.291 ms median / 278.646 ms p90 to 0.114 / 0.115 ms. The
  198,041-character comment case fell from 276.608 / 276.714 ms to
  0.427 / 0.473 ms. Run `node scripts/bench-dhtmlxq.mjs`.
  These measure this parser, not the complete import pipeline. Browser checks
  in all three engines at 1440/390/320 pixels verify that malformed paste
  preserves the current board, then import a valid text file with unfinished
  comment tags and retain its later Unicode note when saved. The regression
  reports click-to-error-DOM timing separately from the automation's wait for
  a stable, clickable button. One diagnostic Chromium run measured 245.73 ms
  before the click and 3.875 ms from the click to the error DOM update; the
  earlier complete action timing must not be treated as a parser stall.
- **Reject malformed collection annotations promptly.** The collection parser
  independently used a backtracking regex to remove `[%xqanalysis ...]` tags.
  A 962,009-character input below its file-size limit took 23,587.8 ms in one
  baseline Node/Vite parser run before rejecting a note over 500 characters.
  It now shares the ordinary importer's linear delimiter scanner, preserving
  the collection's existing treatment of closed and unfinished tags. After
  five warmups, twenty samples of the complete current parser call (including
  typed annotations) measured a 3.357 ms median /
  4.551 ms p95. These are local synthetic parsing measurements,
  excluding file reading, worker startup, rendering, and storage; they are not
  typical-game or device-speed claims. Run `node scripts/bench-pgn-collection.mjs`.
  Browser coverage uploads the near-limit file, expects the specific note-size
  error within five seconds, verifies unchanged storage, then imports a valid
  collection and checks its variations, metadata, selection, and quota failure.
- **Avoid regex backtracking in PGN notes.** Repeated unclosed `[%` annotation
  commands inside a valid comment made the normal importer's note parser rescan
  the remaining text at every opener. A 198,012-character regression took
  6,523 ms before the fix on this machine. Reusing the linear delimiter scanner
  preserves the same bounded note and moves; `node scripts/bench-pgn-comments.mjs`
  now measures a 0.250 ms median / 0.321 ms p95 for that input after five warmups
  and twenty samples. This is isolated parsing of a pathological note, not a
  typical-game or device-speed claim. The browser regression imports the full
  note, navigates to its move, saves it, and checks 1440/390/320px layouts.
- **Avoid wasted searches first.** The confirmed scheduling race is fixed.
  Continue examining search ownership and stop/restart boundaries before changing
  engine budgets. Preserve the full move history when analyzing repetitions.
- **Avoid repeated tree copies.** On this development machine, adding 64 moves
  to an 800-move tree took a median 4.73 ms (p95 5.11 ms) with the old insertion
  algorithm versus 0.25 ms (p95 0.30 ms) with the shared helper. The benchmark
  warmed both implementations, interleaved 50 runs, and checked equal output.
  This isolated Node/Vite JavaScript measurement excludes rendering, engine
  search, and storage; it is not a whole-interaction or phone speed claim.
- **Serialize ancestry once.** Run `node scripts/bench-study-serialization.mjs`
  to compare the former algorithm with the current serializer. On this machine,
  a 1,024-move annotated chain changed from a 1.758 ms median / 2.229 ms p95 to
  0.096 ms / 0.154 ms. The 50 interleaved samples follow warmup and an equal-output
  check. This excludes JSON encoding, storage writes, browser rendering, and
  engine work. The performance gain is in assembling the tree snapshot.
- **MultiPV costs depth.** [Stockfish's UCI documentation][uci] recommends one
  line for maximum performance. The pinned Pikafish `search.cpp` performs a root
  search for each PV. The app already uses one line outside detailed analysis;
  increasing defaults would trade depth for alternatives. Benchmark fixed-time
  depth and responsiveness with 1/3/5 lines before changing the existing choice.
- **Coalesce progress before crossing the worker boundary.** The real network
  download produced a median 4,085 callbacks versus 52 after coalescing, about
  98.7% fewer messages. Five interleaved Chromium samples per implementation used
  fresh contexts, the real 53,719,310-byte network, single-SIMD, one thread, and
  16 MB hash; each completed a depth-one search. Median ready times were 935.1
  and 931.1 ms, effectively unchanged in this small local experiment. This is
  a reduction in queued work, not evidence of faster engine search, rendering,
  or phone startup. Initial/completion/reset reports and byte integrity remain
  covered, including unknown and encoded content lengths. Reproduce with
  `git show 8600929:templates/pikafish.js > /tmp/xiangqi-progress-baseline.js`
  followed by `node scripts/bench-progress-browser.cjs /tmp/xiangqi-progress-baseline.js`.
- **Ordinary compression will not shrink the weights.** The shipped NNUE file
  is 53,719,310 bytes. Node gzip produces 53,732,472 bytes; Brotli quality 4
  produces 53,719,450. Both are slightly larger. Prioritize reliable versioned
  reuse of matching engine/network assets, and investigate smaller compatible
  networks only with strength and parity validation.
- **PGN export is not yet a demonstrated responsiveness bottleneck.**
  `node scripts/bench-pgn-export.mjs` warms ten runs, checks the exported move
  sequence, and times fifty annotated straight-line exports at 128/512/1,024
  plies. On this arm64 macOS machine with Node 26.7.0, median times were
  0.051/0.561/1.993 ms; the 1,024-ply p95 was 2.586 ms. This measures text
  generation only, excluding rendering, clipboard/download work, and engine
  search. The exporter still copies ancestry sets recursively, so revisit its
  scaling before raising study limits. These local timings do not establish a
  phone bottleneck or justify claiming a noticeable UI speedup from a rewrite.
- **Frontend structure remains worth investigating.** The production main
  JavaScript bundle is about 473 kB / 145 kB gzip. Splitting optional study and
  import surfaces could reduce first-load parsing and simplify maintenance.
  The large source file is evidence of complexity, not proof of slow frames.
  Use production traces before claiming a speed improvement.
- **Device behavior still needs direct evidence.** Chromium viewport tests
  verify layout, not phone thermal throttling, memory pressure, touch hardware,
  Safari, or battery drain. Do not tune mobile thread/hash defaults from desktop
  viewport emulation alone.
